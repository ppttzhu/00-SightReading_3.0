# Devil's Advocate Review: Refactor Adventure Stage Guidance

**Reviewer's mandate**: Find every flaw, risk, and oversight. Severity (HIGH/MEDIUM/LOW) and probability (Certain/Likely/Unlikely) assigned to each finding.

---

## Finding 1 (HIGH / Certain): `syncUpsertAdventureStage()` has no unique key to upsert against

The proposal assumes an incremental upsert function is straightforward (tasks.md 3.3, design.md Decision 5). It is not.

**Current `adventure_routes` schema** (migration_add_adventure_paths.sql):
```sql
CREATE TABLE public.adventure_routes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    route_name TEXT NOT NULL DEFAULT 'main',
    stage_order INTEGER NOT NULL,
    UNIQUE(route_name, stage_order)
);
```

The `id` is auto-generated by the DB. The current `save()` does a full DELETE + INSERT, so it never needs to match an existing row. The load function reconstructs client IDs from `source_stage_id + partial DB UUID`, but there is NO way to query back a single row by client ID.

**The proposals's options for upsert are all flawed:**

| Upsert key | Problem |
|---|---|
| `(route_name, stage_order)` | `stage_order` (= `levelNum`) changes when stages are reordered. An incremental update at the old `stage_order` changes the wrong row. |
| `source_stage_id` | Not unique — same source stage can appear multiple times in a route (the code generates IDs like `adventure_route_${sourceStageId}_${index}`). |
| Add a `client_id` column | Requires a schema migration the proposal doesn't mention. When `save()` deletes and re-inserts, this ID would need to be persisted or regenerated. |

**Worst case scenario**: Incremental upsert creates duplicate `(route_name='main', stage_order=N)` rows, violating the unique constraint and crashing the operation. Or the upsert silently updates the wrong row, corrupting the route.

**Verdict**: The proposal must either (a) acknowledge the need for a `client_id` column and add it to the migration plan, or (b) abandon incremental sync and rely solely on the "Publish Route" button (which contradicts Decision 5).

## Finding 2 (HIGH / Likely): Dual sync paths create silent data corruption risk

The current architecture has TWO code paths writing to `adventure_routes`:

1. **Full publish** (`supabaseStorageProvider.save()`): DELETE `WHERE route_name='main'` then INSERT all rows.
2. **Proposed incremental sync** (`syncUpsertAdventureStage()`): Single-row UPSERT.

**Race condition**: If the teacher edits guidance and immediately clicks "Publish Route":

1. `updateAdventureStage()` fires → Zustand store updates (sync)
2. `syncUpsertAdventureStage()` fires (async, fire-and-forget)
3. Full `save()` fires (async) but reads from store snapshot taken at call time
4. Both write to `adventure_routes` concurrently

If step 2's upsert uses `(route_name, stage_order)` or any other key, and step 3's DELETE happens between step 2's read and write, the incremental update writes to a row that's about to be deleted. The subsequent full insert includes the correct data (from the store), so the net result is likely correct — but only by coincidence.

**Long-term divergence**: The `save()` method handles ALL columns. The incremental sync only handles `guidance` and `guidance_images`. If a future change adds a column that `save()` writes but the incremental sync forgets, the two paths diverge systematically. This is a classic dual-write anti-pattern.

**Verdict**: The proposal must either share a single write path or document a transactional approach. Fire-and-forget dual writes to the same table are a maintenance trap.

## Finding 3 (HIGH / Likely): `supabaseStorageProvider.load()` silently drops guidance/guidanceImages

The existing `load()` method (supabaseStorageProvider.ts lines 306-330) selects `*` from `adventure_routes` but maps only these fields to `AdventureStage`:

```typescript
adventureStages = (routeRows as any[]).map((r) => ({
  id: ...
  title: r.title,
  description: r.description || undefined,
  levelNum: r.stage_order,
  sourceStageId: r.source_stage_id,
  sourceModule: r.source_module,
  questionCount: r.question_count,
  unlockRule: 'previous_clear' as const,
  source: (r.source || 'manual') as 'manual' | 'assistant',
  createdAt: ...,
  updatedAt: ...,
}));
```

**`r.guidance` and `r.guidance_images` are never read.** Task 3.2 says "load() reads guidance + guidanceImages from adventure_routes" but this is deceptively simple — it requires:
- Extracting `r.guidance` and `r.guidance_images` from the DB row
- Parsing `guidance_images` from JSONB into `GuidanceImage[]`
- Handling missing/null values gracefully
- Generating correct `id` strings (the current id generation already has edge cases with the `_unknown_` fallback)

The task is listed as a single checkbox item but involves non-trivial data transformations.

## Finding 4 (HIGH / Likely): Guidance suppression removal breaks non-adventure stages

The proposal says in quiz-practice spec.md:
> Scenario: 非冒险关卡不受影响
> WHEN 学生进入 `custom_xxx` 或 `auto_xxx` 格式的关卡
> THEN 系统 MUST 从 `CustomStage.guidance` 读取指导内容
> AND 展示逻辑不变（有则弹，无则跳过）

**This is false.** The "display logic unchanged" claim contradicts the actual change.

Currently, `GuidanceModal` has a "不再提示" (don't show again) checkbox backed by localStorage. For custom/auto stages, a student who has seen guidance once can check this box and never see it again for that stage.

The proposal removes:
- `GUIDANCE_SUPPRESS_KEY` constant
- `readSuppressedMap()` function
- `writeSuppressed()` function
- The checkbox from the modal

After this change, EVERY time a student enters a custom/auto stage with guidance, the modal appears. No suppression possible. This is a real regression for students who practice the same custom stage repeatedly.

**Impact**: Free practice students who revisit stages for revision will be interrupted by guidance every single time. This is especially problematic if guidance contains images — the modal could be large and slow to render.

**Fix needed**: Either keep the suppression mechanism for non-adventure stages, or explicitly document this behavioral change as intentional (and update the spec).

## Finding 5 (MEDIUM / Certain): Teacher confusion with dual-field modal after migration

The migration SQL copies `adventure_routes.description` to `guidance`:
```sql
UPDATE adventure_routes SET guidance = description WHERE guidance IS NULL
```

But `description` is NOT cleared. After migration, every existing adventure stage has:
- `description` = old guidance text (shown on the adventure map card)
- `guidance` = same old guidance text (shown in the modal)

The teacher opens the edit modal and sees both fields populated with identical text. The labels say "关卡说明（显示在闯关地图卡片上）" and "学习指导". But they contain the SAME text. The teacher must:

1. Understand the semantic difference between the two fields
2. Manually decide what to keep in description (card text) vs. guidance (modal text)
3. Edit both fields accordingly

**No migration tooling** is provided to help. The proposal doesn't mention:
- A bulk-clear-description admin action
- A visual hint in the UI when the two fields contain identical text
- A one-click "separate" button

**Probability**: Every teacher who has existing adventure stages will encounter this confusion. Certain.

## Finding 6 (MEDIUM / Certain): CustomStage.guidance becomes orphaned and uneditable

The proposal explicitly removes the guidance editor from `CustomStageEditor` (tasks 6.1-6.3). The data field `CustomStage.guidance` remains in the type definition and is still read by `InteractiveQuiz` for free practice mode.

**Consequences**:
- Existing guidance text on CustomStages is frozen — can never be updated or removed from the UI
- Teachers creating NEW custom stages have no way to add guidance from the UI
- The `updateCustomStage()` store action still accepts `guidance` in its patch, but no UI code calls it with guidance changes
- `CustomStageEditor.handleCreate()` (line 129) still does `guidance: guidance.trim() || undefined`, so the FORM state for guidance persists in code but the UI is being removed

Task 6.3 says "移除相关 state（guidance, uploadStatus, textareaRef, fileInputRef）" — but this `guidance` state variable is also used in `handleCreate()` and `handleEdit()` and `handleUpdate()`. Simply removing the state breaks those functions.

**This is a dead data path**. Either: (a) keep a minimal guidance editor in CustomStageEditor for free practice, or (b) clean up all remaining code paths that reference CustomStage guidance (handleCreate, handleEdit, handleUpdate, the type definition, the store action, InteractiveQuiz's guidance resolution for non-adventure stages).

## Finding 7 (MEDIUM / Certain): Image deletion creates placeholder orphan in guidance text

The proposal says when a teacher deletes an image from the image list:
1. Delete from `adventure_guidance_images` table
2. Remove from `stage.guidanceImages` array
3. NOT delete from Storage
4. Notify teacher

**What's missing**: The `{image:id}` placeholder in the guidance Markdown text is NOT cleaned up. After deletion:
- The guidance text contains `{image:img_abc123}`
- `guidanceImages` no longer has an entry with that ID
- Per the spec (adventure-path spec.md line 35): "WHEN `{image:id}` not found in guidanceImages, system MUST render as raw text"
- So the student sees literal `{image:img_abc123}` in the guidance modal

This is not a crash scenario (the spec handles it gracefully), but it leaves the guidance text with broken visual artifacts that the teacher must manually find and delete.

**Fix**: When deleting an image, either (a) also remove all `{image:<id>}` occurrences from the guidance text, or (b) warn the teacher with a specific message like "Also remove `{image:img_abc123}` from your guidance text."

## Finding 8 (MEDIUM / Likely): `getAdventureStages()` description fallback still references `sourceStage.guidance` after separation

Current `getAdventureStages()` (useAppStore.ts line 303):
```typescript
description: stage.description || sourceStage.guidance,
```

The proposal's whole point is separating "card description" from "guidance." But the description fallback chain still falls back to `sourceStage.guidance`. After the change, when a teacher uses `addToRoute()` with `description = ''`, the card would display `sourceStage.guidance` — which is guidance content, exactly what we're trying to separate.

**Affected scenario**:
1. Teacher adds stage to route. New AdventureStage has `description: ''`, `guidance: ''`.
2. Source CustomStage has `guidance: "注意升降号..."`.
3. Card displays "注意升降号..." — the guidance text!
4. Teacher manually fills guidance in the modal. Guidance is now "注意升降号...学习指导具体内容".
5. Card STILL shows "注意升降号..." (from the fallback), not `description` (which is empty).

The teacher must understand that `description` needs to be filled separately from `guidance`, even though the fallback makes `description` appear populated.

**Fix**: Update the description fallback to NOT include `sourceStage.guidance`:
```typescript
description: stage.description || '',
```

## Finding 9 (MEDIUM / Likely): Redundant image data storage without sync guarantees

The proposal stores image metadata in TWO places:
1. `adventure_routes.guidance_images JSONB DEFAULT '[]'` (in the route row, alongside the stage data)
2. `adventure_guidance_images` table (separate table with full metadata)

**Why both?** The proposal doesn't explain. The JSONB on `adventure_routes` duplicates the same data in the separate table. This creates a sync problem:
- When an image is deleted, both must be updated
- If one write succeeds and the other fails, they diverge
- The `save()` method writes `guidance_images` (JSONB) but the incremental sync also needs to manage the separate table
- The load function needs to reconstruct `GuidanceImage[]` from either the JSONB or the separate table

**Writes are not transactional** — the code does not use Supabase transactions. If the `adventure_guidance_images` write succeeds but the JSONB update fails (or vice versa), the two sources are permanently out of sync.

**Recommendation**: Choose one storage strategy. If the JSONB column exists, the separate table is redundant. If the separate table is needed for management queries, use only that table and derive the array from a JOIN on load.

## Finding 10 (MEDIUM / Likely): `addToRoute()` silently drops source guidance

Current `addToRoute()`:
```typescript
description: source.guidance || '',
```

Proposal changes to:
```typescript
description: '',
guidance: '',
```

This means when a teacher adds a CustomStage that already has guidance written, that guidance is DISCARDED. The teacher must:
1. Add the stage to the route
2. Open the edit modal
3. Remember what guidance was written
4. Rewrite it in the new modal

For teachers with many stages, this is a significant burden. The proposal's justification ("教师应手动填写") is philosophically consistent but practically inconvenient.

**Alternative**: Pre-fill `guidance` from `sourceStage.guidance` on addToRoute, let the teacher modify it. The teacher can still clear it if they want.

## Finding 11 (MEDIUM / Likely): InteractiveQuiz guidance modal title source is broken for adventure stages

In `InteractiveQuiz.tsx` (line 574-585):
```tsx
if (!introDismissed && guidance && stageRecord) {
  return (
    <GuidanceModal
      title={stageRecord.title}
      guidance={guidance}
      ...
    />
  );
}
```

The `stageRecord` variable is defined as `customStages.find(cs => cs.id === stageId)` (line 243). For adventure stages where `stageId` starts with `adventure_route_`, `stageRecord` is ALWAYS `undefined`. So even after fixing the `guidance` lookup, the condition `stageRecord` on line 574 will be falsy — the modal will never show.

The proposal's task 7.1 ("fix guidance finding") and 7.3 ("always show modal") don't address that the modal's own display condition depends on `stageRecord`, and neither does the title source problem.

**Fix needed**: The guidance modal display logic needs to be completely restructured for adventure stages:
```typescript
const guidance = isAdventureStage ? adventureStage.guidance : customStage?.guidance;
const title = isAdventureStage ? adventureStage.title : customStage?.title;
const showModal = !introDismissed && guidance;
```

## Finding 12 (MEDIUM / Unlikely): `{image:id}` placeholder preprocessing for ReactMarkdown is non-trivial

The proposal says to replace `{image:id}` with `<img>` during rendering. But the guidance text is passed through `ReactMarkdown`, which does NOT understand `{image:id}` syntax — it renders as literal text.

The code must preprocess guidance text BEFORE passing to ReactMarkdown:
```
"{image:img_abc123} some text" → "![guidance-image](https://cdn.example.com/img_abc123.png) some text"
```

This preprocessing needs to:
1. Parse the guidance string for `{image:<id>}` patterns
2. Look up each ID in `guidanceImages[]`
3. Replace with standard Markdown image syntax (or HTML `<img>` tag)
4. Handle missing IDs gracefully (render as raw text per spec)

Tasks.md 4.9 says "Markdown preview (ReactMarkdown + image placeholder parsing)" but doesn't detail the preprocessing approach. This is a critical rendering path item that affects both CMS preview and student display.

## Finding 13 (LOW / Likely): Escape key still disabled in GuidanceModal

Current `GuidanceModal` (line 16-24):
```tsx
useEffect(() => {
  const handler = (e: KeyboardEvent) => {
    if (e.key === 'Escape') {
      e.preventDefault();
      e.stopPropagation();
    }
  };
  window.addEventListener('keydown', handler);
  return () => window.removeEventListener('keydown', handler);
}, []);
```

Escape is explicitly disabled. The proposal removes the checkbox but does not mention Escape behavior. If a student accidentally enters a guidance modal and wants to exit, they cannot — Escape does nothing, backdrop click does nothing. They must click "开始答题."

This may be intentional (per the "always show guidance" requirement), but it creates a UX trap. If the guidance text is very long or images are slow to load, the student has no way to bypass.

**Recommendation**: Make Escape work or document that it's deliberately disabled.

## Finding 14 (LOW / Likely): No loading state for guidance data

When guidance contains many images, the modal may be slow to render. There is no:
- Loading indicator while images load
- Skeleton placeholder
- Progressive image loading

The `guidanceImages` could contain multiple images (each potentially several MB if the teacher uploaded large files). The proposal doesn't address this.

**Recommendation**: Add lazy loading for guidance images or a loading state for the modal.

## Finding 15 (LOW / Unlikely): Offline editing silently loses guidance changes

The incremental sync is fire-and-forget (`void syncUpsertAdventureStage()`). If the teacher is offline:
1. Store updates locally (Zustand persist saves to localStorage)
2. `syncUpsertAdventureStage()` is called
3. `hasWriteSession()` returns false because there's no Supabase session
4. Function returns silently — no error, no retry

The teacher thinks guidance is saved. It is saved locally. But when they publish, the full `save()` DOES write to Supabase. So the data eventually reaches the server on publish. However, there's an intermediate period where the local state and remote state disagree.

**Probability**: Unlikely (CMS is typically used with a network connection). But worth noting.

## Finding 16 (LOW / Unlikely): `AutoStage.guidance` added to shared type affects non-adventure consumers

`AutoStage` is used by BOTH `getAllStages()` (for custom/auto stages) AND `getAdventureStages()`. Adding `guidance` and `guidanceImages` to `AutoStage` means:
- `getAllStages()` returns `AutoStage[]` with potentially undefined guidance fields
- TypeScript won't catch if someone uses `stage.guidance` thinking it's populated for all stages
- Any code that maps over all stages (e.g., admin reports) might need to handle mixed source types

**Also**: `CustomStageEditor.tsx` line 51 currently does:
```typescript
const orderedStages: AutoStage[] = getAllStages(module);
```
After the change, these `AutoStage` objects gain guidance fields from the CustomStage type. This is backwards-compatible (guidance is optional), but any future code that reads `stage.guidance` from `getAllStages()` might behave differently than expected.

## Recommended Mitigations

1. **Add `client_id TEXT UNIQUE` column to `adventure_routes`**: This provides a stable upsert key. The full save must preserve these IDs rather than delete+re-insert.

2. **Single write path**: Either make the incremental sync write through the same `save()` method (with a per-row flag), or make `save()` skip rows already written incrementally (e.g., via a dirty-tracking mechanism).

3. **Separate AdventureMap description from guidance explicitly**: Remove `sourceStage.guidance` from the description fallback in `getAdventureStages()`.

4. **Keep suppression for non-adventure stages**: Either add a parameter to GuidanceModal to control whether the checkbox appears, or keep the suppression mechanism and only disable it for adventure routes (by checking the `stageId` prefix at the call site).

5. **Rewrite InteractiveQuiz guidance resolution holistically**: The current code (`stageRecord = customStages.find(...)`) is fundamentally incompatible with adventure stages. The entire guidance resolution block (lines 242-248, 574-585) needs to be restructured to handle both paths.

6. **Migration helper for teachers**: Add a one-click "Separate description from guidance" action in the AdventureEditor that sets `guidance` from `description` and then clears `description` (or offers a new empty card text).
